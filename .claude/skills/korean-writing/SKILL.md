# 한국어 작문 규칙

이 레포에서 쓰는 한국어는 전부 Jessi가 읽는다. 커밋 메시지는 밤마다 블로그 글의 재료가 되므로, 커밋이 어려우면 글도 어려워진다.

Jessi가 짚은 문제는 둘이다.

1. **제가 만든 말을 씁니다.** 개발 개념을 짧은 한국어 이름으로 바꾸면, 그 이름은 저한테만 통하는 말이 됩니다.
2. **영어를 옮긴 말투를 씁니다.** 영어로 생각한 문장을 한국어로 옮기면 낱말은 한국어인데 문장이 어색합니다.

목표는 사람처럼 보이는 것이 아니라 **처음 읽는 사람이 한 번에 알아듣는 것**입니다.

## 먼저: 기술 용어는 그대로 쓴다

커밋, 레포, 배포, 브랜치, PR 같은 개발 용어와 Next.js, Remotion, Vercel, ElevenLabs, Claude 같은 도구·서비스 이름은 번역하지 않고 빼지도 않습니다. 이 블로그는 바이브 코딩으로 무엇을 어떻게 만드는지 보여 주는 곳이라, 용어를 지우면 그 내용이 사라집니다. 10/6 밤 글과 대본이 "커밋"을 전부 "작업 메모"로 바꿔 썼고, Jessi가 짚었습니다. "핵심 단어는 번역하면 안 된다", "기술 용어를 쓰지 말라는 건 이 블로그의 목적에 벗어난다".

어려울 것 같으면 처음 나올 때 한 번만 괄호로 설명을 붙입니다.

- 글: "커밋(작업 메모)이 5개 모이면 글이 나옵니다." "Remotion(코드로 영상을 만드는 도구)으로 렌더합니다." 그다음부터는 그냥 씁니다.
- 내레이션: 괄호는 소리로 읽지 않으므로 "커밋, 그러니까 작업 메모를"처럼 한 번 풀어 말합니다.

아래 규칙 1은 이 레포에서 제가 새로 만든 말에 대한 것입니다. 기술 용어를 바꾸라는 뜻이 아닙니다. 쓰지 않는 것은 파일명·함수명처럼 그 코드 안에서만 통하는 이름과, 커밋에 적힌 내부 용어("판정", "tally" 같은 말)뿐입니다.

## 규칙 1. 이름을 새로 만들지 않는다

개념에 이름을 붙이지 말고 그 일이 무엇을 하는지 문장으로 씁니다. 처음 한 번 풀어 쓴 뒤에도, 짧은 이름으로 바꿔 부르지 않습니다.

| 제가 쓴 말 | 고쳐 쓴 말 |
|---|---|
| 한 줄 커밋은 문턱에 안 센다 | 제목 한 줄만 있고 본문이 없는 커밋은 글을 쓸 만한 커밋으로 치지 않습니다 |
| 돈을 쓰기 전에 거는 문 | AI를 부르기 전에 걸러 냅니다 |
| 절감 손잡이 | 비용을 줄이는 방법 |
| 헛실행 가드 | 쓸 글이 없는 밤에 실행이 여러 번 돌지 않게 막습니다 |
| 넘어가기 장치 | 새 모델을 못 부르면 예전 모델로 다시 부릅니다 |
| 나눠 받는 방식 | 답을 조금씩 받아 모으는 방식 |
| 속사정 | 프로그램이 안에서 판단하는 기준 |
| 재료를 안 본 눈 | 커밋을 읽지 않은 다른 AI |
| 무대를 깐다 | 이 프로젝트가 무엇인지 먼저 소개합니다 |
| 말하는 사람 규칙 한 줄 | "글은 Jessi가 '저'로 말한다"는 규칙 |

**판별법:** 그 말을 Jessi가 이 대화를 안 보고 처음 들었을 때 뜻을 아는가. 모르면 풀어 씁니다.

화면에 실제로 보이는 이름("지난 실행", "삽질 포인트")과 코드 이름(`run.json`)은 써도 됩니다. 코드 이름은 백틱으로 감싸서 코드라는 것을 보여 줍니다.

## 규칙 2. 비유하지 않는다

기술 설명에 비유를 쓰면 비유를 풀어야 뜻이 나옵니다. 문턱, 손잡이, 문, 눈, 무대, 시계, 장치 같은 말을 기술 설명에 쓰지 않습니다. 정말 필요하면 한 문장짜리 하나만 쓰고, 빼도 뜻이 통하는지 확인합니다.

## 규칙 3. 영어를 옮긴 말투를 피한다

| 피할 말 | 쓸 말 |
|---|---|
| A를 통해 B한다 | A로 B한다, A해서 B한다 |
| A에 의해 만들어진 | A가 만든 |
| 기능을 가지고 있다 | 기능이 있다, 기능이 많다 |
| 분석되어진다 | 분석한다, 분석된다 |
| 이 문제에 대해 논의했다 | 이 문제를 논의했다 |
| 교육에 있어서 | 교육에서 |
| 빠르다는 점에서 효율적이다 | 빨라서 효율적이다 |
| 결론적으로, 시사하는 바가 크다 | 빼고 그냥 말한다 |
| 이 변화는 효율을 가져온다 | 이렇게 바꾸니 효율이 올랐다 |

전체 목록과 이유는 `.claude/skills/humanizer`에 있습니다.

## 규칙 4. 문장을 짧게, 주어와 동사를 분명히

- 한 문장에 정보 하나. 쉼표로 절을 이어 붙이지 말고 문장을 나눕니다.
- 명사를 줄줄이 붙이지 말고 동사로 풉니다. "비용 절감 효과 측정" 대신 "비용이 얼마나 줄었는지 쟀다".
- "이것", "그것", "그 문제"처럼 가리키는 말은 바로 앞 문장에 그것이 나왔을 때만 씁니다.

## humanizer에서 쓰지 않는 것

humanizer는 AI가 쓴 글을 사람이 쓴 것처럼 보이게 만드는 도구라서, 이 사이트와 목표가 다른 규칙이 섞여 있습니다.

- **패턴 8–10 띄어쓰기 흩뜨리기**: 쓰지 않습니다. 맞춤법대로 띄어 씁니다.
- **패턴 24 존댓말 끝맺음 섞기**: 쓰지 않습니다. 글과 대본은 "~습니다"로 통일합니다.
- **패턴 21 일부러 묻는 문장 넣기**: 쓰지 않습니다.
- **패턴 6 줄표를 괄호로 바꾸기**: 답변에서는 줄표도 괄호도 줄입니다. 문장을 나누는 쪽을 고릅니다.

## 쓰는 순서

1. 쓴다.
2. 검사기를 돌린다.
   ```bash
   npx tsx scripts/check-korean.ts                  # README·CLAUDE.md·docs
   npx tsx scripts/check-korean.ts --commit --strict  # 방금 쓴 커밋 메시지
   npx tsx scripts/check-korean.ts --text "문장"     # 답변에 쓸 문장
   npx tsx scripts/check-korean.ts --run            # 홈 "지난 실행" 문구
   ```
   "강"은 고칩니다. "약"은 문맥을 보고 판단합니다.
3. 소리 내어 읽듯 다시 읽는다. Jessi가 이 대화를 안 봤어도 알아듣는가.
4. 긴 문서나 글을 새로 쓰면 humanizer 스킬로 한 번 더 본다. 위 "쓰지 않는 것"은 빼고 적용합니다.

검사기에 걸리는 말이 새로 보이면 `scripts/korean-style.ts`의 목록에 더합니다. 그 목록은 밤에 쓰는 글과 쇼츠 대본의 검사에도 그대로 쓰입니다.
